Everything you need to add lightweight UX telemetry to a product page: one browser script, declarative triggers, contextual surveys, optional aggregate heatmaps, and one collector endpoint you own.

Quick start

Host tinyux.js on your own domain and point it at a collector endpoint. The client starts automatically when both data-app-id and data-api-url are present.

product-page.html
<script src="/js/tinyux.js"
  data-app-id="acme-app"
  data-api-url="/collect.php"
  data-config='{
    "surveys": {"maxPerSession": 2, "minIntervalMinutes": 5},
    "exitIntent": {"enabled": true, "survey_id": "exit-survey"}
  }'>
</script>

Upload collect.php next to the script. On the first request it creates its SQLite database in tinyux-data/ and blocks that folder from the web with a deny-all .htaccess. To see where data will live before going live:

terminal
php collect.php --check

Upgrading from v0.1

  • Replace tinyux.js (or tinyux.min.js) and collect.php. The script API and payload contract are backwards compatible.
  • On the first request the collector adds event_uid and survey_uid columns to your existing database. It keeps using tinyux.db next to collect.php until you move it; php collect.php --check explains how. Don't re-run schema.sql on an old database.
  • Cross-origin setups: list your app's origin in $ALLOWED_ORIGINS. v0.1 accepted every origin.
  • mouseSampling is gone; remove it from your config if you set it.
  • Survey prompts now read their colors from --tinyux-* CSS variables. The default look is unchanged.

Declarative triggers

Add attributes to product UI when you want telemetry or a survey without writing custom JavaScript.

TriggerAttributeBehavior
Clickdata-tinyux-trigger="click"Captures element metadata and optionally shows data-tinyux-survey-id.
Section scrolldata-tinyux-trigger="section-scroll"Records section visibility with threshold, cooldown, and once-per-session controls.
Time delaydata-tinyux-trigger="time"Shows a survey after data-tinyux-after-ms, defaulting to 5000 ms.
Exit intentdata-tinyux-trigger="exit-intent"Associates a survey with global exit-intent detection.
html
<button
  data-plan="team"
  data-tinyux-trigger="click"
  data-tinyux-survey-id="upgrade-clarity">
  Upgrade
</button>

<section
  id="pricing"
  data-tinyux-trigger="section-scroll"
  data-tinyux-threshold="0.5"
  data-tinyux-once="session"
  data-tinyux-survey-id="pricing-clarity">
</section>

Surveys

Surveys can be registered programmatically or embedded as JSON in data-tinyux-survey. Supported types are rating (set min and scale), nps (0 to 10), yesno, choice, and text.

js
const ux = window.tinyux.getInstance()

ux.registerSurvey({
  id: 'pricing-clarity',
  type: 'yesno',
  title: 'Pricing clarity',
  question: 'Was this section clear?',
  oncePerSession: true,
  cooldownMinutes: 120,
  ui: { mode: 'corner', position: 'bottom-right' }
})

ux.registerSurvey({
  id: 'exit-survey',
  type: 'choice',
  title: 'Before you go',
  question: 'What stopped you today?',
  choices: ['Pricing', 'Missing feature', 'Just browsing', 'Other']
})

ux.registerSurvey({
  id: 'nps',
  type: 'nps',
  question: 'How likely are you to recommend us to a colleague?',
  followUp: { when: '<=6', question: 'What should we fix first?' }
})

Questions can interpolate element dataset values with {{data-name}}, using safe dataset metadata only.

Survey UI defaults to a blocking center modal, rendered with the native <dialog> element where available so focus stays inside and returns to the trigger afterwards. Set ui.mode to corner for a non-blocking prompt, with position set to bottom-right, bottom-left, top-right, or top-left. Corner prompts never steal focus.

followUp asks one more free-text question only when the first answer matches when: a comparison such as '<=6', a list of values such as ['Pricing', 'Other'], or a single value such as false. The stored response becomes { "value": 3, "comment": "..." }.

Theme prompts with ui.theme (light, dark, or auto) and override any --tinyux-* CSS variable (--tinyux-bg, --tinyux-fg, --tinyux-accent, --tinyux-radius, --tinyux-font) on .tinyux-root in your own stylesheet. Button text comes from ui.labels, so prompts can match your product's language.

Opt-in signals

Each signal is off by default and changes nothing until you turn it on. They all ship in the same file: tinyux.min.js is about 13.6 KB gzipped with every option included.

SPA page views

spa: true records a page_view with path and from whenever the URL path changes without a reload. It uses the Navigation API (Baseline since January 2026) and falls back to wrapping history.pushState/replaceState plus popstate. Pages restored from the back/forward cache also count as page views, with restored: true.

Rage and dead clicks

frustration: true adds two events. A rage_click is three or more clicks within about 700 ms and 24 px of each other, recorded once per burst. A dead_click is a click on a button, link, summary, or button-like role that is followed by no DOM change, no URL change, and no page hide within one second. Both carry coarse x_pct/y_pct, path, viewport, and sanitized element metadata, so heatmap queries work for them too.

sql
SELECT json_extract(event_meta, '$.path') AS path,
       json_extract(event_meta, '$.element.id') AS element,
       event_type, COUNT(*) AS n
FROM events
WHERE app_id = 'acme-app' AND event_type IN ('rage_click', 'dead_click')
GROUP BY 1, 2, 3
ORDER BY n DESC;

Web Vitals (recipe)

tinyux does not bundle performance metrics. If you want them, load Google's web-vitals library and forward its callbacks:

js
import { onLCP, onINP, onCLS } from 'web-vitals'

const ux = window.tinyux.getInstance()
const send = (m) => ux.track('web_vital', { name: m.name, value: Math.round(m.value * 1000) / 1000, rating: m.rating })
onLCP(send)
onINP(send)
onCLS(send)

Aggregate heatmaps

Heatmaps are opt-in and aggregate-only. tinyux records coarse click/tap coordinates as heatmap_point events so you can build a simple density overlay or export later. It does not capture screenshots, DOM snapshots, mouse trails, or replayable sessions.

html
<script src="/js/tinyux.js"
  data-app-id="acme-app"
  data-api-url="/collect.php"
  data-config='{
    "heatmaps": {"enabled": true, "clicks": true, "taps": true}
  }'>
</script>

Heatmap event metadata includes x_pct, y_pct, viewport, path, input, and sanitized element metadata that respects datasetAllowlist and datasetDenylist.

sql
SELECT
  json_extract(event_meta, '$.path') AS path,
  json_extract(event_meta, '$.viewport') AS viewport,
  json_extract(event_meta, '$.x_pct') AS x_pct,
  json_extract(event_meta, '$.y_pct') AS y_pct,
  COUNT(*) AS points
FROM events
WHERE app_id = 'acme-app' AND event_type = 'heatmap_point'
GROUP BY path, viewport, x_pct, y_pct
ORDER BY points DESC;

Identity association

tinyux keeps anonymous client_id and session_id by default. If your app already knows the signed-in user or account, pass that identity explicitly. tinyux does not fingerprint browsers or devices to guess identity.

js
const ux = window.tinyux.getInstance()

ux.identify('user_123', {
  account_id: 'acct_456',
  plan: 'team',
  role: 'admin'
})

ux.track('checkout_started')

You can also provide the initial user in config:

js
tinyux.init({
  appId: 'acme-app',
  apiUrl: '/collect.php',
  user: {
    id: 'user_123',
    account_id: 'acct_456',
    traits: { plan: 'team' }
  }
})

Consent and storage

tinyux does not decide whether you need consent; your policy does. These options make either answer easy to implement.

html
<script src="/js/tinyux.js"
  data-app-id="acme-app"
  data-api-url="/collect.php"
  data-config='{"consent":"pending","respectGPC":true,"storage":"session"}'>
</script>

<script>
  // In your consent banner:
  acceptButton.onclick = () => tinyux.consent(true)
  rejectButton.onclick = () => tinyux.consent(false)
</script>
  • consent: 'pending': events wait in memory, nothing is written to localStorage or sessionStorage, nothing is sent, and no survey appears. consent(true) persists the ids and sends what was buffered; consent(false) discards it and stops tracking.
  • storage: 'none' keeps ids, the retry queue, and survey cooldowns in memory only, so every page load gets a new anonymous id. 'session' keeps them for the tab session.
  • clientIdTtlDays (395 by default) rotates the persistent anonymous id after about 13 months.
  • respectGPC: true drops identify() data when navigator.globalPrivacyControl is true and marks payloads with meta.gpc. respectGPC: 'all' turns tinyux off for those visitors.
  • sampleRate: 0.25 tracks a quarter of sessions; the decision is made once per session.
  • On the server, php collect.php --prune --days=395 deletes rows older than the retention window. Run it from cron.

Payload schema

The client POSTs JSON batches. Unload beacons are sent as text/plain (a CORS-safelisted type, so cross-origin collectors need no preflight), so collectors should parse the body as JSON regardless of content type. Every event and survey answer carries a unique id: store it and ignore repeats, because retries can deliver the same batch twice.

json
{
  "app_id": "acme-app",
  "client_id": "uuid",
  "session_id": "uuid",
  "user": {
    "id": "user_123",
    "account_id": "acct_456",
    "traits": {"plan": "team"}
  },
  "ts": 1781230000,
  "meta": {
    "url": "https://app.example.com/pricing",
    "referrer": "",
    "viewport": {"w": 1366, "h": 768},
    "scroll_pct": 42,
    "focus_ms": 38120,
    "interaction_count": 3,
    "score": 7,
    "user": {
      "id": "user_123",
      "account_id": "acct_456",
      "traits": {"plan": "team"}
    }
  },
  "events": [
    {"id": "3f6b2c1e-...", "type": "interaction", "ts": 1781230001, "meta": {"selector": ".cta"}},
    {"id": "9a0d77c4-...", "type": "heatmap_point", "ts": 1781230002, "meta": {"x_pct": 52, "y_pct": 34, "viewport": "1366x768", "path": "/pricing", "input": "click"}}
  ],
  "surveys": [
    {"id": "c41e09b2-...", "survey_id": "pricing-clarity", "type": "yesno", "response": {"value": true}, "context": {}}
  ]
}

Collector

collect.php is the reference collector: one PHP file using PDO SQLite in WAL mode. It creates its schema on the first request, upgrades v0.1 databases in place, and ignores duplicate events and survey answers by id.

  • Data lives in tinyux-data/ next to the script, protected by a deny-all .htaccess. On nginx, block that folder or set TINYUX_DB_PATH (and TINYUX_LOG_PATH) to a path outside the web root.
  • Requests are same-origin only by default. Add cross-origin apps to $ALLOWED_ORIGINS.
  • The log records app id and counts only. IP addresses are never written to it, and the soft rate limiter keys on a salted hash.
  • Optional request metadata ($CAPTURE_REQUEST_META) stores a salted HMAC of the IP only once TINYUX_IP_SALT is set, plus the user agent if $CAPTURE_USER_AGENT is on.
  • Top-level user data is merged into stored client/session metadata.
  • ux_apps stores app IDs.
  • clients stores anonymous browser client IDs.
  • sessions stores session IDs per client.
  • events stores event id, type, timestamp, and JSON metadata.
  • surveys stores answer id, survey ID, type, response, and context JSON.
  • failed_payloads stores payloads that could not be written, for the retry worker.
terminal and cron
php collect.php --check     # where data lives, plus warnings

*/5 * * * * /usr/bin/php /path/to/collect.php --retry
17 3 * * *  /usr/bin/php /path/to/collect.php --prune --days=395

Privacy defaults

tinyux is not a recorder or fingerprinting library. It never captures screen contents, DOM snapshots, keystroke contents, clipboard contents, camera, microphone, console logs, network logs, or form values by default.

Dataset metadata can still identify people if you put sensitive data in data-* attributes. Use datasetAllowlist for strict deployments.

v0.2 removed the old mouseSampling option, so tinyux records no pointer trails. The collector no longer writes IP addresses to its log. See consent and storage for consent gating, Global Privacy Control, cookieless mode, and retention.

FAQ

Is this a Hotjar or FullStory replacement?

No. tinyux is for targeted telemetry, contextual feedback, and optional aggregate click/tap heatmaps. It is not a replay, screenshot, or visual behavior suite.

Does it work in SPAs?

Yes. Set spa: true and tinyux records a page_view on every client-side route change. The mutation observer also picks up declarative triggers on new elements.

What happens when the network drops?

Failed payloads stay in storage with exponential backoff and are retried on later flushes or the next page load. When the page is hidden, everything still buffered is sent with sendBeacon, and anything the browser refuses is kept for next time. The collector ignores duplicates.

Do I still need a consent banner?

That depends on where you operate and how you configure tinyux. If you need consent, set consent: 'pending' and call tinyux.consent(true) from your banner: nothing is stored or sent before that.

Can I require an API key?

Yes for normal fetch sends. sendBeacon cannot set custom headers, so strict API-key deployments may disable beacon reliance or validate origin/session instead.

Is text survey input safe?

Text surveys can collect personal data because users type free-form content. Use rating, yes/no, and choice surveys when possible.
